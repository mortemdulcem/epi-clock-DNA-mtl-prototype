# makale_revize figürleri: salt görsel, ama pixel-OVERLAY ile Türkçeleştirildi

The 14 epigenetics charts (`scripts/revize/media/img-034..047`) are raster images
extracted from the original `makale.pdf` — there is NO chart-generation script for them
in the repo (`scripts/build_figures*.py` belong to the unrelated TOMEC article). So the
baked-in English chart text cannot be translated by editing-and-re-rendering a generator.

**Solution that works (and was applied to all 14):** faithful pixel-OVERLAY, never
regeneration. The `scripts/revize/figtrans/` pipeline (`overlay.py` engine, `specs.py`
per-figure ops, `run.py` preview→`--apply`→`media/`) fills a bg rectangle over a tightly
measured text box and redraws ONLY the Turkish translation of English *words*. Build with
`node scripts/revize/build/build.cjs`.

**Translation style decisions (keep consistent across figures):** translate English words
only — Mean→Ortalama, Cortex→Korteks, Hippocampus→Hipokampüs, yrs→yıl, (years)→(yıl),
Supplementary Figure→Ek Şekil. "vs"→en-dash "–" (Turkish "vs."=vesaire is a false friend;
"+X yıl" IS literally the difference, so a dash is mathematically exact). KEEP verbatim:
all numbers/±SD/p/CI/n/%/β, Latin names (Nucleus Accumbens, Prefrontal), and abbreviations
(ANOVA, F, Post-hoc, Tukey HSD, CI, NS, EAA, PMI, pH, Horvath, PFC/NAc/Hipp).

**Why this is the honest path:** earlier worry was that dense scatter/volcano plots can't be
regenerated without inventing point coordinates (= fabrication). Overlay sidesteps that
entirely — the underlying chart pixels (points, violins, bars, axes, borders) are never
touched; only word-glyphs are repainted in place.

**How to PROVE zero-hallucination after applying a figure (do this every time):**
1. Border integrity: diff original (`media_en/`) vs applied (`media/`) on the chart's measured
   frame/border coordinates → must be 0 changed pixels.
2. Data-ink safety: count changed pixels OUTSIDE every declared overlay box → must be 0
   (proves you painted only inside intended boxes; untouched kept-lines stay byte-identical).
3. Numeric token equality: regex-extract numbers/p-values/n=/markers from the EN source string
   and from your TR string → token lists must be equal (guards against a mistyped value).
All three passed for the full set incl. S8 (img-047-014) on the final pass.

**How to apply:** if asked again to translate makale figures, use the figtrans overlay
pipeline (don't regenerate), follow the style decisions above, and run the 3-part proof.

## Three recurring glyph/number traps when mechanically cleaning Turkish PDF-extracted DOCX legends
When stripping garbage from pdftotext-derived legends/footnotes, three "safe cleanup" rules each backfire on legitimate content — guard all three or you silently corrupt verbatim data:
1. **Thousands-comma stripping eats statistical df.** A rule turning `10,542`→`10542` also turns `F(4,142)`→`F(4142)`. A comma directly inside a `letter(` group is degrees-of-freedom notation, not a thousands separator. Guard with negative lookbehind `(?<![A-Za-zχ²]\()` so only real thousands collapse.
2. **Bullet-dash splitting eats math minus.** A rule turning ` - ` into a list bullet also splits `y = 0.20 · ln(x) - 3.53` into an orphan `- 3.53`. Real bullets in these legends always precede a LETTER; math minus precedes a digit. Require a letter after the dash: `\s+[-–—]\s+(?=[A-Za-zÇĞİÖŞÜçğıöşü])`.
3. **U+F0B7 Word "•" bullet renders as tofu in MS365.** The Symbol-font bullet leaks into text as a Times New Roman run → shows as □ box. It is pure list furniture (panel labels A./B. + per-line link rendering already give structure), so strip `\s*\uf0b7\s*`→space. Not a content change.
**Verify after every build (architect content-blocks this Turkish medical text):** python zipfile/XML scan asserting — F(4,142) present & F(4142) absent; equation `ln(x) - 3.53` present; no PUA glyphs (0xE000–0xF8FF) remain; body orphan-fragment scan returns only legitimate ALLCAPS section headings (ABSTRACT/KISALTMALAR/TEŞEKKÜR/KAYNAKÇA/EKLER).

## User wants table/figure notes as small-font footnotes hugging the object
Dr. Nurcan's standing preference for makale_revize: every note/legend that sits BELOW a table or figure must be **9pt (sz=18)** and **snug to the object** ("tabloya bitişik"), not body-size with a blank-line gap. Table TITLE stays above the table (academic standard) — only the under-object note shrinks. **How to apply:** post-table notes (renderStream emitTail), main-figure legends (figBlock), and supp-figure legends (SUPP loop) all render at sz:18, before:0, small after, line:240; the table's required trailing separator paragraph is kept minimal (sz=8 mark) so nothing forces a full blank line between grid and note. Body prose resuming after a figure (not a note) stays 11pt — keep that distinction. This is formatting-only (zero-hallucination): text/numbers byte-identical, verify the note + its values survive.

## 27 tables consolidated into 10 — render each member as its OWN sub-table, never one merged composite
Reviewer asked to merge the 27 source tables into 10 display tables. **First design (abandoned) and WHY:** one bordered `<w:tbl>` where members with DIFFERENT column counts were stacked and aligned via `gridSpan` to the widest panel. That single root cause produced all 3 later complaints at once — (1) long words wrapped mid-word in the squeezed columns, (2) every member's footnote stacked together below the whole composite, (3) ragged/misaligned borders where a 5-col panel's gridSpanned cells didn't line up with an 8-col panel. **Design that works:** each grouped member renders as its OWN clean `<w:tbl>` at its OWN caption; only members that share an identical column count (e.g. a group of same-width segments) may stay combined in one `unifiedTable`. The group emits the umbrella "Tablo N." caption + ref ONCE (at first member), then each member table, and the existing emitTail drops each member's footnote directly below ITS table (fixes #2 with no pre-extraction/dup risk). `TABLE_LAYOUT`/`groupInfo` (build.cjs) drives display order 1..10; caption number is the FIXED display number, not render-order. Expect `<w:tbl>` count = total member count (e.g. 28), not 10. **Render order = display order only because each group's members all fall inside ONE renderStream range in order — verify that trace before trusting fixed numbering.**
**Why:** merging different-column panels into one grid is a false economy — it looks unified but mathematically cannot align borders or size columns, and forces footnote stacking. Separate sub-tables under a shared caption read as "one table" to the reviewer while staying clean.

## Dense-table long-word wrapping (e.g. "Metamfetamin") — proportional widths + tight margins + font step-down
A long single UNBREAKABLE word wraps mid-word wherever it sits — and it can be a COLUMN HEADER, not just a row label (e.g. "Metamfetamin" is a header in one table, a row label in another). So "just widen column 0" is wrong. Fix in `unifiedTable` (lib.cjs), all three needed together: (1) `<w:tblLayout w:type="fixed"/>` + content-proportional `gridCol` widths where each column's weight = the longest single-token (word) length across header+all rows of every panel (clamp ~3..24); long multi-word cells still wrap across lines, which is intended. (2) tight `tblCellMar` left/right ~36 dxa — Word's default 108-dxa padding alone pushed a borderline word onto a 2nd line. (3) font step-down by column count: 7pt (sz=14) at ≥8 cols, 8pt (sz=16) at 7 cols, 9pt (sz=18) otherwise. **Verify by RENDERING (pdftoppm), not just XML** — the gridCol widths can be correct yet the word still wrap by one glyph because of cell padding; only the rendered image tells you. sz=8 (4pt) empty paragraphs before each table are pre-existing spacers, not content.
**Verification gotcha (cost a wasted pass):** when proving cell preservation by substring-searching the stripped document.xml, you MUST un-escape XML entities first (`&lt;`→`<`, `&gt;`→`>`, `&amp;`→`&`). Otherwise every cell containing `<`/`>`/`&` (p-values like `<0.001`, ranges like `>50 yaş`, `β & %`) is a FALSE "missing". After un-escaping, all 991 constituent cells matched → 0 loss.

## Figure numbering must follow appearance order, not source order
The 6 main figures are injected at topically-relevant body sections (via INLINE_FIG keyed by heading line), so a figure's SOURCE number ("Şekil 4: Çalışma Kohortu") may land first. Displayed number must be assigned by ORDER OF APPEARANCE (first injected = Şekil 1), set in INLINE_FIG `num`. When renumbering: a legend's own desc may contain a self-reference ("Şekil 4'te sunulan...") that must be remapped from the source number to the new display num. Also the legend label-strip regex must REQUIRE `[:.]` (`/^Şekil\s*\d+\s*[:.]\s*/`) — an optional `[:.]?` wrongly eats sentence references like "Şekil 4'te", leaving an orphan "'te sunulan".

## Body-text 3-decimal stats: use PERIOD, not comma — build.cjs stripThousands eats `0,893`→`0893`
The same `stripThousands` guard documented above (for legend df-notation) ALSO runs on body prose via `applyFixes`. Its rule `(?<![A-Za-zχ²]\()(\d{1,3}),(\d{3})(?!\d)` collapses any bare 3-decimal COMMA number: `0,893`→`0893`, `0,160`→`0160`, `0,928`→`0928`. **So write 3-decimal stats in makale.txt body with a PERIOD (`0.893`, `0.928`, `0.160`)** — which also matches the article's own existing AUC convention (`0.928`, `1.000`). Safe as commas: 1–2 decimals (`0,80`, `%97,3`) and 4+ decimals (`0,0012`) — neither matches the 3-digit pattern. **Verify after every build**: unzip `word/document.xml`, strip tags, assert each stat string is present AND its mangled form is absent — but first check the mangled form isn't a legit substring elsewhere (`0893`=DOI `…ng108932`; `0660`=accession `GSE50660`; `0129`=table value) before treating a hit as corruption. REPORT.md is NOT processed by build.cjs, so comma-decimals there are fine and need no conversion.
