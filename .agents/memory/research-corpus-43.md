# 43-PDF research corpus

User supplied 43 public Google Drive PDF links (saved list in `attached_assets/`), asking me to "learn them line by line / deep-learn and develop a neural network." Downloaded to `attached_assets/research_corpus/NN.pdf` via a resumable curl script (`scripts/research/fetch_corpus.sh`, IDs in `scripts/research/ids.txt`). Inventory: `scripts/research/CORPUS_INVENTORY.md`. ~22,425 pages, ~983 MB.

**Key finding / constraint:** Despite the user expecting "mixed books + data," **all 43 are reference/textbooks — there is NO labeled training dataset (images/measurements/CSVs) among them.** Book 14 turned out text-layered (not scanned). Book 22 (Spitz & Fisher, Medicolegal Investigation of Death, 553 pp) was the only truly scanned book — now fully OCR'd.

**Why this matters:** You cannot train a real supervised CNN/Siamese model "from these resources" — they give methods + domain knowledge, not training data. Honest buildable options are: (a) a corpus "brain" = retrieval Q&A grounded in the books (no hallucination, cites pages); or (b) train a real model later on the user's OWN data (thesis 3D-CT orbital images, or ChiroBench signature images). User said "learn line by line for the work."

**What was built (the "learning"):** Full text extracted to `attached_assets/research_corpus/text/NN.txt` (page-separated by `\f`), chunked page-tracked into Postgres table `corpus_chunks` (~24,255 chunks across all 44 books, COMPLETE) with a `tsvector` FTS GIN index. Query tool: `node scripts/research/ask.cjs "query" [k]` returns book+page-cited passages. Indexer/builder: `scripts/research/index_corpus.cjs`. To re-index ONE book after changing its text: `DELETE FROM corpus_chunks WHERE book='NN'` (the indexer's `ON CONFLICT DO NOTHING` keeps stale rows otherwise) + `UPDATE corpus_books SET done=false WHERE book='NN'`, then run the indexer (it skips books where done=true).

**Book 44 (added later, MOST important per user):** Handbook of Anthropometry (Springer, ed. Preedy), 3042 pages, text-layered, drive id `14RFE3QlZpSgKqdepFA-uHplJ0uRrXiQ_`. This is the DIRECT primary source for the orbital-morphometry/sex-determination thesis (has orbit height/width, external orbital surface area, sex/age/ethnic measurement methodology). 4,798 chunks. Big PDFs like this time out in one pdftotext call (~9 pages/sec) → extract in page ranges (`pdftotext -f s -l e`) to /tmp parts, then concatenate in numeric order; \f page separators are preserved across parts so page citations stay correct.

**Page-citation bug fixed (critical for zero-hallucination):** original chunker's final `flush(pages.length)` was off-by-one (trailing `\f` phantom page) and chunks spanned huge empty-page gaps. Fixed in `chunkBook`: track `lastNonEmptyPage` (flush with it, never pages.length), skip empty pages, and a `MAXSPAN=6` guard caps a chunk's page range. Verified across all books: 0 page_end overflow vs pdfinfo, 0 spans >6. Re-run = TRUNCATE corpus_chunks/corpus_books, `node index_corpus.cjs`, then `UPDATE corpus_chunks SET tsv=to_tsvector('simple',content) WHERE tsv IS NULL`.

**Embeddings constraint:** The Replit AI/modelfarm proxy (`AI_INTEGRATIONS_OPENAI_BASE_URL`) does NOT support `/embeddings` (returns 400 "not supported") even though app code at server/routes.ts calls `openai.embeddings.create` — that path is effectively dead. So semantic vector search via the proxy is not possible; used Postgres full-text search instead (also better for reproducibility). For local semantic embeddings you'd need a local model (xenova/transformers) — not installed.

**Gotchas:** (1) `pkill -f tesseract` / `pkill -f <pattern>` MATCHES ITS OWN COMMAND LINE and self-kills the running bash (exit 143, no output) — never pkill -f a pattern that appears in your own command. (2) nohup/`setsid`/`disown` detached background jobs DIE when the bash tool returns (process-group teardown) — for any long (>2 min) job, run it as a **workflow** instead (`configureWorkflow({name, command, outputType:'console', autoStart:true})` via code_execution); it survives across tool calls, poll `getWorkflowStatus` / output files, then `removeWorkflow`. A resumable script (skip pages whose output exists) makes restarts harmless. (3) Drive large files: `https://drive.usercontent.google.com/download?id=ID&export=download&confirm=t` avoids the HTML virus-scan interstitial. (4) `bc`/`column` NOT installed; use awk/node. (5) OCR (tesseract 5.3.4, system dep; ocrmypdf NOT installed) is FAST when done right: set `OMP_THREAD_LIMIT=1` so each tesseract uses 1 thread, run 8 in parallel (nproc=8) — book 22's 553 pages finished in ~5 min in a workflow. Earlier "10s/page, too slow" was a measurement artifact: dying background tesseracts were still burning CPU. DPI: 150 → blank body pages; **250 == 300 quality but ~40% faster** (sweet spot). See `scripts/research/ocr22_300.sh` (resumable, 250 DPI).
